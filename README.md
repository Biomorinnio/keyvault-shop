# keyvault-shop

Тестовое задание Fullstack-разработчик — магазин цифровых товаров (ключи,
пополнения, подписки, гифт-карты).

**Рабочая версия: https://keyvault-shop.onrender.com/** — бесплатный тариф
Render, инстанс засыпает после ~15 минут простоя, первый запрос после сна
может занять до минуты (подробности и почему это ожидаемо — в разделе
«Деплой» ниже). Локальный запуск (см. следующий раздел) — рабочий запасной
вариант, если инстанс в этот момент спит или недоступен.

## Запуск локально

Требуется Node.js **22.13.0+** (LTS-линейка 22.x) или **23.4.0+** — с этих
версий встроенный модуль `node:sqlite` работает без флага. Модуль появился
раньше, в 22.5.0, но там и вплоть до 22.12.x он доступен только за флагом
`--experimental-sqlite` (без флага `require("node:sqlite")` упадёт с ошибкой);
если по какой-то причине вы на такой версии — запускайте
`node --experimental-sqlite src/server.js`. Внешние нативные зависимости не
нужны в любом случае — не требует Python/node-gyp.

```bash
cd backend
npm install
npm start
```

Сервер поднимется на `http://localhost:3000` и раздаёт оттуда же:
- фронтенд-витрину (`frontend/index.html` и статику);
- REST API (`/orders`, `/payment/mock`, `/webhook/payment`, `/admin/...`, `/promo/apply`).

SQLite-файл (`backend/data.sqlite`, WAL-режим) создаётся и засеивается пулом
тестовых ключей и промокодами автоматически при первом старте.

Отступление от изначально выбранного стека: узкое место при разработке —
`better-sqlite3` требует нативной сборки (node-gyp/Python), которых не было в
окружении, поэтому вместо него используется встроенный в Node 22+
`node:sqlite` (тот же синхронный API, `BEGIN IMMEDIATE` работает так же).

## Деплой

Сервис — единственный Node-процесс (Express раздаёт и API, и статику
фронтенда), поэтому на Render это один Web Service без отдельного статик-сайта
и без внешних управляемых сервисов (БД встроенная, в контейнере).

Фронтенд лежит в `frontend/` рядом с `backend/`, а не внутри него
(`backend/src/server.js` отдаёт его через
`express.static(path.join(__dirname, "..", "..", "frontend"))`). Render не
позволяет сервису с `Root Directory: backend` видеть файлы вне этой папки —
по документации Render, «files outside your service's root directory are not
available to the service at build time or at runtime». Поэтому `Root
Directory` нужно **оставить пустым** (= корень репозитория), а на подпапку
`backend` указывать прямо в командах — это и есть рекомендуемый Render способ
для такого монорепо. При пустом `Root Directory` виден весь чекаут целиком, и
относительные от `__dirname` пути до `frontend/` резолвятся штатно.

Конфигурация Web Service на Render (бесплатный тариф):

| Поле | Значение |
| --- | --- |
| Root Directory | *(пусто — корень репозитория)* |
| Build Command | `npm install --prefix backend` |
| Start Command | `npm start --prefix backend` |
| Runtime | Node |

Проверено вручную: `npm install --prefix backend` и `npm start --prefix
backend`, запущенные из корня репозитория (то есть ровно так, как это сделает
Render при пустом Root Directory), стартуют сервер идентично обычному `cd
backend && npm start`.

Node.js версия зафиксирована файлом `.node-version` (значение `22.13.0`) в
корне репозитория — именно его увидит Render, так как Root Directory пустой.
Render определяет версию Node в таком порядке приоритета: переменная
окружения `NODE_VERSION` → файл `.node-version` → файл `.nvmrc` → поле
`engines` в `package.json` → версия по умолчанию (которая может быть заметно
старше 22.13 и не даёт `node:sqlite` без флага). Поле `engines: { "node":
">=22.13.0" }` в `backend/package.json` тут Render автоматически не найдёт
(в корне репозитория своего `package.json` нет), но при пустом Root Directory
`.node-version` в корне и так стоит выше в приоритете, так что это не имеет
значения; `backend/.node-version` оставлен как второй рубеж на случай, если
конфигурацию когда-нибудь поменяют на `Root Directory: backend`. Версия Node —
самая вероятная причина падения деплоя на этом стеке, поэтому она закрыта в
первую очередь.

Переменные окружения задавать не нужно: `PORT` подставляет сама Render, и
сервер уже слушает `process.env.PORT` с фоллбэком на `3000` для локального
запуска (`backend/src/server.js`).

Особенности бесплатного тарифа и как они учтены:

- **Эфемерный диск.** На free tier диск не персистентный, `backend/data.sqlite`
  (в `.gitignore`) может пересоздаваться с нуля при каждом деплое или
  рестарте. Это ожидаемо: при старте процесс всегда пересоздаёт схему и
  засеивает БД детерминированными данными (`backend/src/db/index.js`,
  сиды в `backend/src/data/`) — товары (`INSERT OR IGNORE`), пул ключей и
  промокоды. Путь к файлу БД (`DB_PATH`) резолвится относительно кода, а не
  от внешнего тома, так что ничего вовне контейнера не требуется. Проверено
  вручную: полное удаление `data.sqlite*` и старт с нуля — сидинг
  отрабатывает и каталог, и пул ключей заполняются полностью (5012 товаров,
  12582 ключа).
- **Сон после ~15 минут простоя.** ⚠️ Честно предупреждаем: на бесплатном
  тарифе Render инстанс засыпает примерно через 15 минут без запросов, и
  первый запрос после сна может занимать **до минуты** — контейнер
  поднимается заново, процесс стартует, БД пересоздаётся из сида. Это
  ожидаемое поведение платформы, а не баг приложения. При замере на инстансе,
  который не успел полностью остыть (промежуточное состояние, не полный
  холодный старт), первый запрос занял ~10 секунд — это не гарантия и не
  верхняя граница, полный подъём контейнера с нуля дольше; ориентируйтесь на
  «до минуты».
  После пробуждения всё работает штатно, включая SSE (см. ниже) — джоба
  автоснятия брони (`backend/src/services/reservationExpiry.js`) читает
  `reserved_until` из БД по расписанию (`setInterval`, раз в секунду по
  умолчанию), а не хранит состояние в памяти процесса. Проверено вручную: в
  БД была создана бронь с `reserved_until` в прошлом, процесс перезапущен
  (эмуляция пробуждения после сна) — на первом же тике после старта бронь
  помечена `expired`, а ключ вернулся в `available`. Значит после реального
  пробуждения Render просрочки, накопившиеся во время сна, корректно
  подчищаются, а не зависают до первого живого запроса.
- **SSE за прокси Render.** `/api/events` (`backend/src/routes/events.js`)
  отправляет заголовки `Content-Type: text/event-stream`,
  `Cache-Control: no-cache`, `X-Accel-Buffering: no`, вызывает
  `res.flushHeaders()` сразу после первого события и шлёт heartbeat
  (`:ping`) каждые 25 секунд — раньше, чем типичный таймаут простаивающего
  соединения на прокси. В проекте нигде не подключён compression
  middleware, так что ответу нечем буферизоваться на пути от Express до
  прокси.

## Как проверить защиту от гонок

Все скрипты — чистый Node (`fetch` + `Promise.all`), без внешних зависимостей.
Сервер должен быть запущен (`npm start` в `backend/`).

```bash
node scripts/race-webhook.js       # 50 параллельных вебхуков с одним event_id
node scripts/race-double-click.js  # 2 параллельных "Купить" по одному заказу
node scripts/race-out-of-order.js  # вебхук приходит раньше создания заказа
node scripts/race-promo.js         # параллельное применение промокода с лимитом 3
node scripts/race-last-item.js     # 2 и 50 параллельных POST /orders на последнюю единицу
node scripts/race-double-buy.js    # 2 параллельных POST /orders на один SKU — эмуляция двойного клика "Купить"
```

Каждый скрипт читает базовый URL из переменной окружения `BASE_URL`
(по умолчанию `http://localhost:3000`), поэтому тем же скриптом можно бить и
в задеплоенный на Render инстанс, не поднимая ничего локально:
`BASE_URL=https://keyvault-shop.onrender.com node scripts/race-last-item.js`.

Каждый скрипт печатает диагностику и завершается с кодом `0` (`✅ PASS`) или
`1` (`❌ FAIL`). Пять из шести детерминированно проходят как "заявленное
поведение не нарушено": `race-webhook` и `race-double-click` проверяют, что
ключ на заказ выдаётся не более одного раза (через
`GET /admin/keys-for-order/:orderId`), `race-out-of-order` — что отложенное
событие применяется при создании заказа, `race-promo` — что из 10
параллельных попыток применить промокод с `max_uses=3` успевают ровно 3,
`race-last-item` — что последнюю единицу получает ровно один заказ.
`race-double-buy` устроен иначе: он не проверяет "заказов должно остаться
один", а проверяет целостность данных (каждому созданному заказу — ровно
один уникальный ключ, без задвоения); то, что оба параллельных запроса
создают по заказу — ожидаемый и разобранный отдельно результат, см. раздел
«Двойной клик «Купить» и параллельные заказы» ниже.

## Архитектура решений

Ниже — объяснение каждого механизма корректности, продуманного до написания
кода, своими словами и с привязкой к файлам.

### Идемпотентность вебхука оплаты

Платёжка может доставить один и тот же вебхук несколько раз (at-least-once).
`event_id` — `PRIMARY KEY` в таблице `webhook_events`
(`backend/src/lib/idempotency.js`, `recordWebhookEvent`). Обработчик сначала
пытается вставить событие; если вставка упала на конфликте PK — событие уже
видели, ничего не делаем и отвечаем `200 OK`. Бизнес-логика (переход статуса,
запуск выдачи) выполняется только если вставка реально прошла. Это защищает
и от повторной доставки, и от гонки, если два одинаковых вебхука пришли
одновременно: конфликт PK в SQLite разрулит только один из них как "новый".

### Атомарный захват заказа на доставку (гонка 50 параллельных вебхуков)

Даже когда `event_id` разный (например, обычная повторная доставка с новым
событием или несколько разных событий по одному заказу), переход
`paid → delivering` и резерв ключа обёрнуты в одну синхронную транзакцию
`BEGIN IMMEDIATE` (`backend/src/services/issuance.js`, `claimForDelivery`).
`BEGIN IMMEDIATE` в SQLite сериализует конкурентных писателей на уровне БД:
пока одна транзакция не закоммитится, следующая ждёт. Перед переходом
проверяется текущий статус заказа (`canTransition`) — переход возможен только
из `created`/`paid`/`out_of_stock`/`delivery_failed`. Итог: 50 параллельных
вызовов эквивалентны последовательной обработке, реально выполнится только
первая транзакция, остальные увидят "заказ уже не в стартовом статусе" или
"доставка уже идёт" (`outcome: "in_progress"`) и не будут дублировать работу.

Если предыдущая попытка выдачи была прервана (например, процесс упал после
резервирования ключа, но до вызова поставщика), `claimForDelivery` сначала
ищет уже зарезервированный на этот заказ ключ и переиспользует его вместо
резервирования нового — так повторный заход не оставляет "зависшие" ключи в
статусе `reserved`.

### Атомарный захват ключа

Резервирование ключа — не `SELECT`, потом `UPDATE` (это гонка: два процесса
могут прочитать один и тот же свободный ключ), а один атомарный `UPDATE`:

```sql
UPDATE keys_pool SET status = 'reserved', order_id = ?
WHERE code = (SELECT code FROM keys_pool WHERE sku = ? AND status = 'available' LIMIT 1)
```

`changes === 0` означает, что подзапрос не нашёл свободного ключа — заказ
переводится в `out_of_stock` (восстановимое состояние, не падение сервера).

### Идемпотентность запроса к поставщику (ловушка "таймаут ≠ отказ")

`request_id` детерминирован от `order_id` и конкретного поставщика
(`orderId:A`, `orderId:B`) и записывается в `issuance_requests` **до** вызова
заглушки поставщика. Наш HTTP-клиент ждёт ответ ограниченное время
(`CLIENT_TIMEOUT_MS`, по умолчанию 2000 мс — специально короче, чем
`timeoutDelayMs` заглушки, иначе таймаут никогда не воспроизвести в тестах).
Если наш клиент не дождался ответа, мы не знаем, успел ли поставщик выдать
код — поэтому `issuance_requests` остаётся в статусе `pending`, а не
помечается как ошибка. Повтор (ручной через `retry-issue` или следующий
вебхук) обязан переиспользовать тот же `request_id`: если для него уже есть
сохранённый `code`, он возвращается без нового обращения к поставщику.

Сама заглушка поставщика (`backend/src/services/createSupplier.js`) со своей
стороны воспроизводит то же поведение "тайм-аут не отменяет уже принятое
решение": как только запрос с данным `request_id` не завершился однозначной
ошибкой, код фиксируется в памяти заглушки *до* искусственной задержки. Повтор
с тем же `request_id` — в том числе после нашего собственного таймаута —
получает тот же код мгновенно, без нового обращения к "поставщику": один и
тот же запрос не может неожиданно выдать второй код. Однозначная ошибка
(`roll < failRate`), наоборот, ничего не запоминает — повтор с новым
`request_id` вправе получить другой исход.

Если поставщик A вернул однозначную ошибку (не таймаут) — вызывается
резервный поставщик B с независимым `request_id` (`orderId:B`). Если A
"завис" (таймаут), заказ уходит в `delivery_failed` без обращения к B: у нас
нет способа узнать, не выдаст ли A код позже с тем же `request_id`, и
параллельный запрос к B создал бы риск задвоения кода на один заказ.
Повторная выдача (см. ниже) при следующей попытке снова начинает с A и
переиспользует его `request_id`, так что более ранний "зависший" ответ A не
потеряется.

### Вебхук раньше создания заказа (out-of-order)

Вебхук может прийти до того, как заказ появился в БД (например, в тестовом
сценарии `race-out-of-order.js`, или в реальности — из-за рассинхронизации
внешних систем). `event_id` в `webhook_events` не привязан внешним ключом к
существующему заказу, поэтому событие в любом случае сохраняется и
обработчик отвечает `200 OK` (`backend/src/routes/webhook.js`), даже если
`orders` ещё не содержит такой `order_id` — событие остаётся в статусе
`processed = 0`. При создании заказа (`POST /orders`,
`backend/src/routes/orders.js`) сразу после вставки строки вызывается
`applyPendingEventsForOrder`, которая находит необработанные события для
этого `order_id` и применяет их по порядку получения. Так событие не
теряется и не обрабатывается дважды (флаг `processed` в `webhook_events`
исключает повторное применение тем же путём, что и полная идемпотентность
вебхука).

### Восстановление после сбоя

`out_of_stock` и `delivery_failed` — не финальные, а восстановимые статусы:
админ-эндпоинт `GET /admin/orders?status=out_of_stock` их показывает, а
`POST /admin/orders/:id/retry-issue` (`backend/src/routes/admin.js`) вызывает
ту же функцию `attemptIssue`, что и обычный путь выдачи. Так как
`request_id` детерминирован от `order_id`, повтор попадает в ту же ветку
идемпотентности запроса к поставщику и не может создать второй ключ на один
заказ — он либо переиспользует уже сохранённый код, либо (если ключ пула
пополнили) резервирует новый ключ ровно один раз благодаря атомарному
`UPDATE` из раздела выше.

### Промокоды с лимитом использований под нагрузкой

Лимит соблюдается атомарным условным инкрементом:

```sql
UPDATE promocodes SET used = used + 1 WHERE code = ? AND used < max_uses
```

`changes === 0` означает, что лимит уже исчерпан — в этом случае вся
транзакция (`backend/src/routes/promo.js`, `POST /promo/apply`) откатывается,
включая уже выполненную вставку в `promo_usages`. Составной ключ
`promo_usages (order_id, promo_code)` защищает от повторного применения
одного и того же кода к одному и тому же заказу (при конфликте PK промокод
считается уже применённым, без повторного списания лимита). Скидку в любом
случае считает сервер по данным из `promocodes` — расчёт на клиенте
(`frontend/app.js`) чисто визуальный и не используется как источник истины.

### Прочие решения

- **Цена и скидка — только на сервере.** `POST /orders` берёт цену из
  таблицы `products` в БД (`backend/src/services/catalog.js`, `getProduct`) по
  `sku`, а не от клиента; скидка по промокоду тоже всегда пересчитывается
  сервером (см. выше).
- **Выдача не блокирует ответ вебхука.** `attemptIssue` может занять секунды
  (заглушки поставщика умеют "зависать") — `backend/src/services/webhookProcessor.js`
  запускает её после отправки `200 OK`, не дожидаясь результата; клиент
  отслеживает прогресс через `GET /orders/:id`.
- **Явный `id` при создании заказа.** `POST /orders` может принять `id` от
  клиента вместо генерации на сервере — это нужно только для сценария
  "вебхук раньше заказа" (`scripts/race-out-of-order.js`), где тест заранее
  знает `id`, шлёт вебхук первым и затем создаёт заказ с тем же `id`.
  Единственная защита от произвольного значения — конфликт `PRIMARY KEY`
  (`409`, если такой `id` уже занят): формат/уникальность заранее не
  проверяются, и в продакшене это позволило бы клиенту навязывать свои
  order id. Это осознанный компромисс ради воспроизводимости
  out-of-order-теста в рамках тестового задания, а не недосмотр.
- **Пул ключей распределён round-robin по каталогу.** Тестовый список ключей
  из задания не привязан к конкретным `sku`, поэтому при засеивании
  (`backend/src/data/keysPool.js`) ключи раздаются по кругу по всем товарам
  каталога, чтобы у каждого `sku` был свой запас для тестов.
- **Админ-эндпоинты без авторизации.** Осознанное упрощение для тестового
  задания — полноценная авторизация условиями задания не требовалась.
- **Переключатель валют на витрине визуальный.** Цена везде хранится и
  считается в RUB; клик по `$`/`₸`/`₽` меняет только активное состояние
  кнопки, без пересчёта суммы — это соответствует условиям задания.
- **Двойной клик "Оплатить" не требует отдельной защиты на `/payment/mock`.**
  Два параллельных вызова `POST /payment/mock` по одному заказу — оба
  легитимны сами по себе (заказ ещё в статусе `created`) и каждый планирует
  свой вебхук со своим `event_id`. От двойной выдачи защищают уже описанные
  выше механизмы дальше по цепочке: идемпотентность обработки вебхука
  (переход `created → paid` происходит только один раз) и атомарный захват
  ключа — независимо от того, сколько вебхуков в итоге пришло.

### Каталог и цена в БД, большой сгенерированный набор

Цена и наличие живут в БД (таблица `products` + пул `keys_pool`), а не в
JS-массиве. `backend/src/data/catalog.js` остался только сид-данными исходных
12 товаров; единственный его потребитель в рантайме — сидинг в
`backend/src/db/index.js`. Источник истины по цене в рантайме — таблица
`products` (`backend/src/services/catalog.js`).

Помимо 12 исходных товаров каталог засеивается ~5000 сгенерированных
(`backend/src/data/generateProducts.js`) — это нужно, чтобы на следующем этапе
доказать мгновенный поиск по большому каталогу. Генератор детерминирован:
названия, типы, цены и число ключей каждого товара считаются от фиксированного
сида через маленький PRNG (mulberry32). Благодаря этому при каждом старте
получается ровно тот же набор, и идемпотентный сидинг через `INSERT OR IGNORE`
не плодит дубли и не меняет количество ключей у товара между рестартами.
Каждому сгенерированному товару выдаётся 0–5 ключей, поэтому в каталоге есть и
товары в наличии, и распроданные (`stock === 0`). Сгенерированные названия не
содержат символов `&`, `<`, `>`, `"`, поэтому карточки безопасно вставляются в
разметку без экранирования — как и исходные 12 товаров.

### Остаток считается по запросу, не материализуется

Остаток товара — это `COUNT(*)` свободных ключей
(`backend/src/services/catalog.js`, `getStock`:
`keys_pool WHERE sku = ? AND status = 'available'`), а не отдельное поле-счётчик.
Отдельное поле пришлось бы держать в консистентности с пулом ключей при каждой
брони/выдаче/пополнении — лишний источник рассинхронизации. Подсчёт опирается на
индекс `idx_keys_pool_sku_status (sku, status)` и дёшев. `GET /api/catalog`
отдаёт первые 50 товаров с посчитанным `stock` у каждого (полноценные
поиск/пагинация — отдельный этап).

### Админ-эндпоинты управления ценой и складом

Чтобы проверяющий мог руками менять витрину и наблюдать реакцию, добавлены
`PATCH /admin/products/:sku` (смена цены), `POST /admin/products/:sku/keys`
(добавить N свободных ключей) и `DELETE /admin/products/:sku/keys` (убрать N
свободных ключей — эмуляция «товар закончился»). Как и остальная админка, они
без авторизации. Новые ключи получают случайный суффикс в `code`, чтобы не
столкнуться по `PRIMARY KEY` ни с сид-ключами, ни между повторными вызовами.

### Живая витрина через Server-Sent Events

Изменения цены и наличия транслируются всем открытым вкладкам в реальном времени
через Server-Sent Events, а не WebSocket. Причины: поток строго односторонний
(сервер → клиент, клиент ничего не шлёт в этот канал), у браузерного
`EventSource` есть встроенное автопереподключение — это без единой строчки
reconnect-кода закрывает требование «работает после обрыва связи»; и SSE не
тянет за собой дополнительную зависимость (WebSocket потребовал бы, например,
`ws`), работает поверх обычного HTTP.

`backend/src/services/realtime.js` — реестр подключённых клиентов (`Set` из
`res`-объектов) и `broadcast(event, data)`, который пишет каждому клиенту кадр
`event: …\ndata: …\n\n`. `backend/src/routes/events.js` — эндпоинт
`GET /api/events`: отдаёт заголовки `Content-Type: text/event-stream`,
`Cache-Control: no-cache`, `Connection: keep-alive`, отключает буферизацию на
прокси (`X-Accel-Buffering: no`) и сразу флашит заголовки. Каждые 25 секунд шлётся
комментарий-heartbeat `:ping`, чтобы прокси и браузер не рвали «молчащее»
соединение. Клиент обязательно снимается с реестра в обработчике
`req.on("close")` (и там же гасится интервал heartbeat) — иначе закрытые
соединения копились бы и `broadcast` писал бы в мёртвые сокеты (утечка).

Типы событий: `price_changed` (`{ sku, price, currency }`) и `stock_changed`
(`{ sku, stock }`). На этом этапе события эмитятся только из админских
эндпоинтов (`PATCH /admin/products/:sku` → `price_changed`;
`POST`/`DELETE .../keys` → `stock_changed` с пересчитанным остатком). Эмит идёт
**после** успешного коммита транзакции, а не внутри неё: иначе клиенты могли бы
увидеть изменение, которое затем откатилось.

На клиенте (`frontend/app.js`) при загрузке страницы открывается `EventSource`
на `/api/events`. Обработчики событий точечно правят DOM конкретной карточки по
`sku` (цену, строку остатка, доступность кнопки «Купить») — грид целиком не
перерисовывается, поэтому нет мигания списка и не сбрасывается позиция скролла.
При `stock_changed` с нулём кнопка становится задизейбленной и показывает «Нет в
наличии», при возврате в наличие — обратно. В углу шапки есть индикатор
состояния соединения («онлайн» / «переподключение»), который отражает
`onopen`/`onerror` у `EventSource`. Ключевой момент для устойчивости к обрыву
связи: при каждом успешном (пере)подключении клиент заново запрашивает
`GET /api/catalog` и синхронизирует витрину — пока связь отсутствовала, могли
прийти изменения, которые клиент пропустил; без этой ресинхронизации данные
после разрыва остались бы устаревшими навсегда.

### Бронь ключа при оформлении и честная гонка за последнюю единицу

Ключ резервируется не после оплаты, а в момент оформления заказа
(`POST /orders`, `backend/src/routes/orders.js`). Иначе можно было бы оплатить
товар, которого физически уже нет: между кликом «Купить» и приходом вебхука об
оплате последний ключ мог уйти другому покупателю. Теперь захват ключа и
создание заказа — одна транзакция `BEGIN IMMEDIATE`: внутри неё выполняется тот
же атомарный `UPDATE keys_pool SET status='reserved', order_id=? WHERE
code=(SELECT … WHERE sku=? AND status='available' LIMIT 1)`. Если
`changes !== 1` — свободных ключей нет, заказ **не создаётся вообще**, клиент
получает `409 { error: "out_of_stock", message: "Товар только что раскупили" }`.
Если ключ захвачен — создаётся заказ в статусе `created` с
`reserved_until = now + TTL`, и ответ включает `reserved_until`, чтобы фронт
сразу знал, сколько осталось до снятия брони.

Так решается гонка за последнюю единицу: `BEGIN IMMEDIATE` сериализует
конкурентных писателей, а `LIMIT 1` + проверка `changes === 1` гарантируют, что
последний ключ достанется ровно одному заказу. Все остальные параллельные
`POST /orders` увидят `changes === 0` и получат честный отказ `409 out_of_stock`
без создания «оплаченного заказа без товара» — оплачивать нечего, заказа нет.
Сценарий проверяется скриптом `scripts/race-last-item.js`.

Резервирование ушло из выдачи: `claimForDelivery`
(`backend/src/services/issuance.js`) больше не ищет свободный ключ, а берёт
именно тот, что уже закреплён за `order_id` бронью. Ветка `out_of_stock` при
оплаченном заказе в нормальном флоу недостижима (ключ забронирован ещё при
оформлении), но статус и логика восстановления сохранены намеренно — на случай,
если ключ по какой-то причине пропал, и для админского `retry-issue`.

### Автоснятие брони по таймеру

Бронь снимается фоновой джобой в том же процессе
(`backend/src/services/reservationExpiry.js`, `setInterval` раз в секунду),
никаких внешних воркеров/очередей не нужно — процесс один, и `node:sqlite` с
таймерами в event loop прекрасно уживается. Каждый проход в одной транзакции
`BEGIN IMMEDIATE` находит заказы `status='created'` с `reserved_until < now`, по
каждому возвращает ключ в пул (`status='available'`, `order_id=NULL`) и переводит
заказ в `expired`. Срок брони читается из БД (`orders.reserved_until`), а не из
таймера в памяти: при перезапуске процесса брони не теряются — джоба сама
подберёт просроченные записи. `stock_changed` с пересчитанным остатком по
затронутым `sku` эмитится после коммита, поэтому у всех вкладок вернувшийся в
продажу ключ загорается одновременно.

TTL брони — константа `RESERVATION_TTL_MS` (`backend/src/lib/reservation.js`,
по умолчанию 3 минуты). Для проверки истечения её можно уменьшить через
переменную окружения, например `RESERVATION_TTL_MS=5000 npm start` — тогда бронь
снимется через 5 секунд.

Остаток товара меняется теперь в трёх точках, и в каждой `stock_changed`
эмитится после коммита: при создании заказа (бронь забрала ключ,
`POST /orders`), при истечении брони (ключ вернулся, джоба выше) и при
`payment_failed` — там ключ тоже возвращается в пул
(`backend/src/services/webhookProcessor.js`), чего раньше не было: неоплаченный
заказ не должен держать ключ забронированным.

### Проверка цены перед оплатой

`POST /payment/mock` сверяет `order.amount` с актуальной ценой товара из БД
(с учётом уже применённой скидки: `product.price - order.discount_amount`). Если
цена изменилась после создания заказа — оплата не проводится, возвращается
`409 { error: "price_changed", current_price, order_amount }`. Это закрывает
требование «новая цена видна до оплаты, а не после» не только визуально, но и на
уровне API: заплатить по устаревшей цене нельзя. Чтобы согласиться с новой ценой,
клиент вызывает `POST /orders/:id/accept-price` — эндпоинт поднимает `amount`
заказа до актуального, после чего оплата проходит.

### Страница оформления с обратным отсчётом

Оформление — отдельный экран, идентификатор заказа держится в query-параметре
URL (`/?order=ord_xxx`), а не в `localStorage`. Благодаря этому корректно
работают кнопка «Назад», прямая ссылка и обновление страницы: при загрузке с
параметром `order` состояние восстанавливается запросом `GET /orders/:id`
(эндпоинт отдаёт и заказ, и товар), а обратный отсчёт считается от
серверного `reserved_until`, а не от локального таймера, запущенного при клике —
поэтому после перезагрузки счётчик продолжается, а не начинается заново.

Клик «Купить» на карточке теперь только оформляет заказ (`POST /orders`) и
переходит на этот экран; сама оплата — уже там. Поведение отсчёта: пока бронь
жива — тикающий таймер и активная кнопка «Оплатить»; по истечении таймер
останавливается, показывается «Бронь истекла», кнопка оплаты убирается и
предлагается вернуться к товару. Если оплата успела пройти — отсчёт скрывается и
показывается статус выдачи, а при `delivered` — код ключа. Если товар подорожал,
пока заказ ждал оплаты, новая цена видна прямо на экране (заказ переопрашивается
раз в 2 секунды), и оплата идёт по подтверждённой новой цене
(`accept-price` → `payment/mock`).

Отказ `409 out_of_stock` при клике «Купить» обрабатывается инлайн-модалкой
«Товар только что раскупили» с предложением вернуться к каталогу (без
`alert`), и карточка сразу помечается как «Нет в наличии».

### Изменение цены видно во время брони, а не только в момент оплаты

До этого шага экран оформления узнавал о новой цене только по опросу раз в
2 секунды (`poller` в `initCheckout`) — формально в пределах требования
(до оплаты), но с задержкой до 2 секунд и без визуального акцента. Теперь
экран оформления подписан на тот же `EventSource`, что и витрина: единственное
SSE-соединение на страницу, `frontend/app.js`, `connectRealtime()` при
`price_changed` не только красит карточку в каталоге, но и рассылает
`document.dispatchEvent(new CustomEvent("realtime:price_changed", …))`.
`initCheckout` слушает это событие, и если `sku` совпадает с открытым
заказом — сразу (без ожидания следующего опроса) обновляет цену товара в
памяти и перерисовывает экран: старая сумма зачёркивается, рядом — новая,
и появляется баннер «Цена изменилась, подтвердите новую сумму». Опрос
раз в 2 секунды оставлен как есть — это резервный канал синхронизации на
случай разрыва SSE-соединения (см. раздел про живую витрину выше), а не
единственный источник обновления.

Кнопка «Оплатить» в этом состоянии меняет текст на «Подтвердить новую цену
и оплатить»: по клику сначала уходит `POST /orders/:id/accept-price`, потом
`POST /payment/mock` — это уже было реализовано на бэкенде и до этого шага
(логика в `pay()`), не хватало только мгновенной видимости изменения на
экране. Логика симметрична и для подешевевшего товара — `priceChanged()`
сравнивает суммы без учёта знака разницы.

### Двойной клик «Купить» и параллельные заказы

Проверка: `scripts/race-double-buy.js` посылает 2 параллельных
`POST /orders` на один SKU без общего `id`, эмулируя ситуацию, когда браузер
всё же успевает отправить два запроса для одной покупки (см. ниже, когда это
реально возможно). Результат детерминирован — **оба запроса создают
отдельный заказ и резервируют разные ключи**: `POST /orders` не требует и не
получает от клиента ничего, что связывало бы два запроса между собой, а
`createOrderWithReservation` (`backend/src/routes/orders.js`) резервирует
ключ для каждого запроса независимо, ровно так, как задумано для двух
*разных* покупателей, торгующихся за один товар (см. «Бронь ключа при
оформлении и честная гонка за последнюю единицу»). У приложения нет понятия
пользователя/сессии, поэтому сервер принципиально не может отличить «два
клика одного человека» от «двух разных людей, кликнувших почти одновременно»
— это не забытая защита, а прямое следствие отсутствия авторизации в этом
тестовом задании.

Само по себе создание второго заказа не бьёт по данным: ключ у каждого
заказа свой и не пересекается (проверяется в `race-double-buy.js`), а если
оплачен будет только один — второй сам вернётся в пул по TTL
(`reservationExpiry.js`), просто временно проездит бронь до истечения
таймера. Реальный риск — не задвоение ключа, а UX и временная просадка
остатка: один невнимательный клик человека держит чужой ключ недоступным до
`RESERVATION_TTL_MS`.

Единственное место, где с этим стоит бороться — фронтенд, потому что именно
там есть представление о «том самом клике», которого нет на сервере.
Защита (`frontend/app.js`, `startCheckout`): кнопка синхронно, до первого
`await`, переводится в `disabled` — этого уже достаточно против буквального
двойного клика мышью или Enter/Space по одной и той же кнопке, потому что
disabled-элемент не диспетчеризует новый `click` (проверено вручную: два
`btn.click()` подряд производят один `POST /orders`). Поверх этого добавлен
`pendingCheckoutSkus` — `Set` занятых прямо сейчас SKU, проверяемый первой
строкой `startCheckout` и снимаемый в `finally` — это защита не от мышки, а
от менее очевидных путей повторного вызова той же функции для того же SKU
(например, повторный рендер карточки в момент запроса), которую сложнее
проверить вручную, но которая ничего не стоит держать включённой всегда.

Полноценно закрыть само дублирование запросов (а не только его следствие на
кнопке) можно только добавив на сервер понятие сессии/пользователя и
привязывая резерв к ней — это отдельная фича авторизации, выходящая за рамки
задания.

### Устойчивость экрана оплаты к разрывам, перезагрузке и повторным кликам

Источник истины для экрана оформления — всегда `GET /orders/:id`, а не
локальное состояние вкладки: `refresh()` вызывается сразу при загрузке,
каждые 2 секунды опросом и сразу после любой попытки оплаты. Из этого
свойства бесплатно следуют несколько требований к устойчивости, ничего
дополнительно чинить не пришлось:

- **Кнопка «Назад» после оплаты и обновление страницы.** URL несёт только
  `order_id` (см. раздел про страницу оформления выше), поэтому и
  возврат назад, и `F5` в любой момент заново запускают `initCheckout` с
  чистого листа и сразу подтягивают актуальный статус — включая финальный
  (`delivered` с кодом, `payment_failed` и т.д.), а не тот, что был на экране
  до перехода. Проверено вручную: заказ, довалидированный до `delivered`
  после `F5`/повторного перехода по `?order=`, сразу показывает код ключа, а
  не кнопку «Оплатить» или бронь.
- **Обновление в момент активной брони.** Отсчёт таймера всегда считается от
  `order.reserved_until`, пришедшего с сервера (`remainingMs()`), а не от
  локального времени клика — поэтому обновление страницы не продлевает и не
  сбрасывает бронь визуально.

Один сценарий требовал явного изменения — **обрыв связи в момент оплаты**.
До этого шага `pay()` в `catch`-блоке (сетевая ошибка у `fetch`, то есть сам
запрос не доехал или не вернулся) просто разблокировала кнопку «Оплатить»
заново, не проверяя, что произошло на сервере — а `POST /payment/mock`
отвечает `202` и запускает вебхук уже после того, как ушёл ответ; если
именно ответ потерялся, оплата на сервере вполне могла пройти. Со старым
кодом пользователь в этот момент видел снова активную кнопку «Оплатить» без
всякого статуса ошибки — обманчиво нейтрально, и мог кликнуть повторно.
Исправлено: `catch` теперь вызывает тот же `refresh()`, что и обычный путь,
и уже он решает, что показать — если заказ по факту оплачен (или уехал
дальше по статусам), кнопка «Оплатить» скрывается вместе с остальным UI для
терминальных статусов; если нет — переигрывает как раньше. Проверено вручную
подменой `window.fetch` для `/payment/mock` (запрос реально уходит через
исходный `fetch` в фоне, но промис для `pay()` отклоняется, как при разрыве
соединения) — экран корректно доходит до «Готово! Заказ выдан» без ложного
сообщения об ошибке оплаты и без повторной отправки `POST /payment/mock`.
- **Повторная оплата уже оплаченного заказа.** Кнопка «Оплатить» скрыта для
  всех статусов, кроме `created` (`render()`), поэтому фронт физически не
  предлагает платить второй раз — обращаться к идемпотентности вебхука
  (см. выше) в норме не требуется, она остаётся подстраховкой на случай
  прямых запросов в обход интерфейса.
- **Двойной клик «Оплатить».** Флаг `payAttempted` + `elPay.disabled = true`
  выставляются синхронно в начале `pay()`, до какого-либо `await` — проверено
  вручную тремя последовательными `.click()` по кнопке: `POST /payment/mock`
  уходит ровно один раз.

### Поиск и фильтры по каталогу

`GET /api/catalog` (`backend/src/routes/catalog.js`, `services/catalog.js`,
`searchCatalog`) принимает `q` (подстрока по `name`), `type` (точный фильтр
по `products.type`), `page`/`limit` и необязательный `sort`. Ответ —
`{ products, total, page, limit }`: без `total` фронт не смог бы посчитать
число страниц и показать «Найдено N» до того, как получит вообще все
совпадения. `limit` всегда клампится к `[1, 100]` (`MAX_LIMIT = 100` в
`services/catalog.js`) независимо от того, что просил клиент, — иначе один
запрос с `limit=999999` вытянул бы весь каталог за раз.

Оба фильтра — обычные `?`-параметры, `type` и `q` никогда не подставляются в
SQL строкой: `type` идёт готовым значением в `WHERE p.type = ?`, `q` — в
`WHERE p.name LIKE ? ESCAPE '\'` уже обёрнутым в `%…%` через `escapeLike`,
которая экранирует `\`, `%` и `_`, чтобы поиск по буквальному `%` или `_` в
запросе не превращался в неожиданный wildcard (проверено: `?q=%25` (`%`) и
`?q=_` находят 0 совпадений, а не половину каталога).

Сортировка по умолчанию, когда есть `q`, — не порядок вставки, а простая
релевантность: сперва товары, у которых `name` начинается с запроса
(`CASE WHEN p.name LIKE ? THEN 0 ELSE 1 END`), затем остальные совпадения по
алфавиту — так поиск «gta» поднимает «GTA V …» выше, чем случайное вхождение
подстроки в середине названия. Без `q` — исходный порядок `p.rowid`. Явный
`?sort=price_asc|price_desc|name_asc` переопределяет это через фиксированный
whitelist SQL-фрагментов (`SORTS` в `services/catalog.js`) — значение параметра
никогда не попадает в `ORDER BY` как текст, только как ключ словаря, поэтому
`?sort=DROP TABLE products` просто не находит совпадения и молча откатывается
к сортировке по умолчанию (проверено вручную).

Здесь честно нужно сказать про индекс: `idx_products_name` — обычный
B-tree-индекс, он ускоряет точное совпадение и `LIKE 'префикс%'`, но не может
ускорить `LIKE '%подстрока%'` — у паттерна с `%` в начале нет диапазона для
range scan по индексу, обе стороны неизбежно требуют скана. Для честного
префиксного поиска пришлось бы или ломать UX (не находить «Steam» внутри
«Пополнение Steam 500 ₽»), или заводить FTS5-таблицу. Смотрели на реальных
числах: на 5012 товарах (`node -e` с прямым вызовом `searchCatalog`, без HTTP)
самый широкий подстрочный поиск (`q: "a"`, совпадает почти со всем каталогом) —
**~2 мс** на запрос, точечный (`q: "steam"`) — **~1.7 мс**, фильтр по `type`
(использует `idx_products_type`) — **~0.2 мс**. Это на два порядка меньше
условленных 50 мс, поэтому FTS5 сейчас не нужен: полный скан 5 тысяч строк в
SQLite тривиально быстрый, а добавлять виртуальную таблицу и синхронизировать
её с `products` — сложность без сегодняшней пользы. Если каталог вырастет на
порядки (сотни тысяч товаров) — тогда стоит завести `products_fts` (FTS5,
`content=products`) и переключить `q`-фильтр на `MATCH`, не трогая остальной
контракт эндпоинта.

### Поиск на витрине: debounce, отмена устаревших ответов, без мигания

Строка поиска (`#searchInput`) и ссылки мега-меню «Каталог» с `data-type`
(см. ниже) пишут в общий `searchState = { q, type, page }`
(`frontend/app.js`). Любое изменение состояния сразу зеркалится в адресную
строку через `history.replaceState` (`syncSearchUrl`) — не `pushState`,
иначе каждый символ добавлял бы запись в историю и «Назад» пришлось бы жать
посимвольно. При загрузке страницы `searchState` восстанавливается из
`location.search` до первого рендера, поэтому прямая ссылка вида
`/?q=steam&type=giftcard&page=2` сразу открывает те же результаты — без
лишнего клика или мигания «сначала пусто, потом заполнилось».

**Debounce.** Ввод в строке поиска планирует `runSearch` через
`setTimeout(…, 250)` (`scheduleSearch`), сбрасывая предыдущий таймер при
каждом новом символе — реальный запрос уходит один раз, через 250 мс после
последнего нажатия, а не на каждую букву. Явные действия (Enter, клик по
кнопке поиска, клик по категории, пагинация) вызывают `runSearch()` напрямую,
в обход задержки.

**Отмена устаревших ответов.** Каждый вызов `runSearch` первым делом
абортит предыдущий незавершённый запрос (`searchAbortController.abort()`)
и заводит новый `AbortController`. Это не «поздний ответ игнорируется по
номеру попытки» — соединение обрывается по-настоящему, устаревший `fetch`
никогда не долетает до `renderSearchResults`. Проверено вручную: подменили
`window.fetch`, чтобы ответ на `q=slowquery` искусственно завис на 3 секунды,
затем через 500 мс (запрос ещё не вернулся) сменили фильтр на
`q=steam&type=giftcard` — итоговый `abortedCount` стал `1` (медленный запрос
реально прерван, не просто проигнорирован), а витрина показала «Найдено: 164»
/ «Steam Gift Card…», то есть результат второго, а не первого запроса. Без
`AbortController` при такой гонке медленный ответ на «slowquery» мог прийти
позже и затереть уже показанные, более свежие результаты по «steam».

**Без мигания списка.** `renderSearchResults` не делает
`grid.innerHTML = …` — вместо этого `diffRenderGrid` сверяет новый список
товаров с уже отрисованными карточками по `data-sku`: переиспользует и
переставляет существующие DOM-узлы, создаёт только реально новые, удаляет
только реально пропавшие. Пока ответ не пришёл, на экране остаются старые
карточки без исчезновения; когда придёт — меняются точечно, без
`innerHTML`-скачка и без сброса скролла. Индикатор загрузки (`#searchLoading`)
— отдельная ненавязчивая надпись рядом со счётчиком «Найдено», не
перекрывающая и не подменяющая сам грид. Freshness данных для переиспользуемых
карточек (цена/остаток могли устареть между двумя выдачами) гарантируется тем
же путём, что и живые SSE-обновления витрины: после диффа `renderSearchResults`
вызывает `applyPriceChange`/`applyStockChange` по `sku` для каждого товара —
это те же функции, что точечно правят карточки по событиям `price_changed` и
`stock_changed`, поэтому и живые обновления цены/остатка продолжают работать
на отфильтрованной/отпагинированной выдаче без отдельного кода. После
переподключения `EventSource` (см. раздел про SSE) `resyncActiveView`
пересинхронизирует именно активный экран — результаты поиска, если поиск
активен, иначе обычные полки.

Пока активен поиск/фильтр, три статичные полки витрины (`#popularSection`,
`#recommendedSection`, `#otherSection`) скрываются, показывается секция
`#searchResults` со своим гридом, счётчиком, пагинацией («← Назад / Стр. X из
Y / Вперёд →», в духе TTL — сервер не отдаёт больше `MAX_LIMIT` за раз, поэтому
без пагинации до части каталога было бы не добраться) и кнопкой сброса,
возвращающей к обычной витрине. Пустой результат — отдельное сообщение
(`#searchEmpty`), а не пустой грид без объяснения.

**Меню категорий.** Ссылки в выпадающем «Каталог» — маркетинговый мокап на
6 колонок (Steam/PlayStation/Xbox/Nintendo/Battle.net/Подборки) без связи с
реальной схемой данных, где типов ровно четыре: `key`, `topup`, `subscription`,
`giftcard`. Вместо того чтобы выдумывать несуществующее сопоставление,
`data-type` проставлен только там, где подпись однозначно соответствует
реальному типу — «Игры и DLC» → `key`, «Пополнение баланса» / «Прямое
пополнение» → `topup`, «Подарочные карты» → `giftcard`, «PS Plus» / «EA Play» /
«Xbox Game Pass» / «NS Online» → `subscription` (это реальные игровые
подписки, а не натяжка). Один делегированный обработчик клика на
`#catalogMenu` ловит клики по `[data-type]`, остальные пункты
(«Коллекционные карточки», «Смена региона», «Скидки 90%», сайдбар с «Игры и
игровые сервисы» и т.п.) остаются декоративными — под них нет ни отдельного
измерения в `products`, ни осмысленного способа отфильтровать по ним, не
изобретая несуществующую таксономию.
